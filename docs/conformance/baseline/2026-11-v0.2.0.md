# Conformance baseline 2026-11 (v0.2.0)

The first run of the 41-check default suite against three cores, with the
verdicts of [ADR-0011](../../adr/0011-conformance-verdicts-gates-and-grouping.md).
How a baseline is run and how to read the verdict words is in
[README.md](README.md).

- Date: 2026-11-12, started 04:51 UTC; one run per core, the three at the
  same time, each in its own testbed on the same host.
- Results for **31 of the 41 checks** are published below. Ten checks are
  left out for all three cores; see [Results withheld](#results-withheld).

## Findings

Each finding was checked against the N2 capture taken during the run, or,
where named, against the capture from an earlier run against the same core
builds. Frame numbers refer to this run's N2 capture; the captures are kept
with the run records, outside the repository.

### GTPU-UNKNOWN-TEID-ERRIND: SD-Core and free5GC (FAIL)

The check sends a G-PDU to the UPF's N3 address with a TEID the UPF has not
allocated (`0x7FABCDEF`) and expects a GTP-U Error Indication (message type 26)
carrying that TEID: TS 29.281 7.3.1 has the UPF discard the G-PDU and, for a
non-zero TEID, return an Error Indication. The SD-Core UPF and the free5GC UPF
sent no Error Indication within the check's 4 s bound; both answered GTP-U
Echo Requests sent before the G-PDU and after the bound, so the path was up.
The Open5GS UPF returned the Error Indication with the TEID within 1 ms. This
run's capture covers N2 only; the behaviour is confirmed in the N3 capture of
the earlier run (same core builds, same result).

### NGAP-HANDOVER-COMMAND-TRANSFER: free5GC (WARN); NGAP-HANDOVER-CANCEL-ACK: free5GC (BLOCKED)

The check performs an intra-system N2 handover and expects a HANDOVER COMMAND
whose PDU Session Resource Handover List items each carry a Handover Command
Transfer (TS 38.413 8.4.1.2, 9.2.3.2). TS 38.413 describes the AMF's answer to
a HANDOVER REQUIRED without obliging it to prepare the handover, so a refusal
is WARN for its availability impact rather than FAIL. free5GC sent the HANDOVER
REQUEST to the target gNB, received its HANDOVER REQUEST ACKNOWLEDGE (frame 438)
and then answered the source gNB with HANDOVER PREPARATION FAILURE, cause
radioNetwork 7, ho-failure-in-target-5GC-ngran-node-or-target-system (frame 439,
1 ms later). The handover-cancel check needs a prepared handover first, so it
reports BLOCKED under this one. The same result appears in the earlier run's
capture.

This matches a known free5GC AMF bug, fixed on the AMF's main branch by
[free5gc/amf@532c8298a](https://github.com/free5gc/amf/commit/532c8298aea6379603920f7e9cb1954dd764d9f9)
("fix: retain selected target TAI during N2 handover"). That commit is five
commits after the AMF in free5GC v4.3.0 (AMF tag v1.4.6, `9fc0ac3f`) and is in
no release at the time of this run. ORBIT has not been run against an AMF that
includes it.

### NAS-REG-REJECTED-NSSAI: free5GC and Open5GS (FAIL); SD-Core (SKIP)

The check registers a UE whose Requested NSSAI holds only an S-NSSAI the core
does not serve (SST 1, SD `eeeeee`), with NSSAA and ER-NSSAI indicated as not
supported. TS 24.501 5.5.1.2.5 (condition b) 2) of cause #62) then calls for a
REGISTRATION REJECT with 5GMM cause #62 "No network slices available", and,
from V16.6.0, a Rejected NSSAI IE listing the rejected S-NSSAI.

- free5GC rejected the registration after the security mode control procedure
  with cause #111 "Protocol error, unspecified" (frame 866), not #62.
- Open5GS rejected it with cause #62, but the REGISTRATION REJECT is four
  octets, `7e 00 44 3e`, with no Rejected NSSAI IE (frame 761).
- SD-Core accepted the registration with its default S-NSSAI (SST 1, SD
  `010203`) in the Allowed NSSAI, which takes the #62 rule out of play; the
  check declares that outcome SKIP.

### NAS-PDU-UNKNOWN-DNN: Open5GS (FAIL)

The check requests a PDU session for a DNN the core does not serve and expects
either a PDU SESSION ESTABLISHMENT REJECT or the un-forwarded 5GSM message sent
back in a DL NAS TRANSPORT with 5GMM cause #90 or #91 (TS 24.501 6.4.1.4.1,
5.4.5.2.5 a) 1), 5.4.5.3.2). Open5GS answered with a 5GMM STATUS carrying cause
#91 "DNN not supported or not subscribed in the slice" (frame 819) and nothing
else within 10 s. SD-Core answered with a PDU SESSION ESTABLISHMENT REJECT;
free5GC returned the 5GSM message.

### NAS-RETRANSMIT-NEW-COUNT: SD-Core, free5GC and Open5GS (FAIL)

With the REGISTRATION COMPLETE withheld, the AMF retransmits the REGISTRATION
ACCEPT on each T3550 expiry (TS 24.501 5.5.1.2.8 c)). TS 24.501 4.4.3.1 has the
sender increase the NAS COUNT by one after each new or retransmitted
SECURITY PROTECTED 5GS NAS MESSAGE, so each retransmission should be protected
at a higher COUNT. In all three cores every retransmission is byte-identical to
the first transmission: the same sequence number (1) and the same MAC. The
T3550 check's capture shows the first transmission and all four
retransmissions, 6 s apart, identical in each core; the earlier run's capture
shows the same. The retransmission timing itself conforms
(NAS-T3550-ACCEPT-RETRANSMIT passes on all three).

### NAS-T3560-AUTH-RETRANSMIT: SD-Core and free5GC (FAIL)

With the AUTHENTICATION RESPONSE withheld, TS 24.501 5.4.1.3.7 b) has the AMF
retransmit the AUTHENTICATION REQUEST on each of the first four T3560 expiries
and, on the fifth, abort the procedure and release the N1 NAS signalling
connection. SD-Core and free5GC sent the AUTHENTICATION REQUEST five times at
6.0 s intervals (SD-Core frames 2275 to 2287, free5GC frames 2431 to 2463), and
then sent nothing for that UE: no UE CONTEXT RELEASE COMMAND in the 36 s before
the next check started. Open5GS sent the same five requests, then an
AUTHENTICATION REJECT and a UE CONTEXT RELEASE COMMAND 6 s after the fifth. The
earlier run's capture shows the same for all three.

### NGAP-UNKNOWN-UE-SURVIVES: SD-Core (FAIL)

The check sends an UPLINK NAS TRANSPORT with an AMF UE NGAP ID and a RAN UE NGAP
ID the AMF never allocated and expects an ERROR INDICATION, with the NG
association still working afterwards (TS 38.413 10.6, 8.7.5.2). SD-Core sent
nothing back on the association within 3 s of the stimulus (frame 1483), and
the association stayed up. free5GC and Open5GS answered with
ERROR INDICATION, cause radioNetwork 14, unknown-local-UE-NGAP-ID.

### NGAP-NGSETUP-MISSING-TALIST: free5GC (FAIL)

The check sends an NG SETUP REQUEST without the Supported TA List, a mandatory
IE with criticality reject (TS 38.413 9.2.6.1), and expects an NG SETUP FAILURE
as TS 38.413 10.3.5 requires for a missing reject IE. free5GC sent no answer
of any kind within 4 s (frame 1709 is the request); the association survived,
and a fresh NG Setup right after the bound completed (frames 1718, 1721).
SD-Core and Open5GS answered with NG SETUP FAILURE.

### NGAP-RAN-CONFIG-UPDATE-TRANSFER-SYNTAX: SD-Core (DEVIATION)

The check sends a truncated RAN CONFIGURATION UPDATE and expects an ERROR
INDICATION (TS 38.413 10.2, a "should"). SD-Core sent nothing within 3 s
(frame 1811 is the stimulus) and the association survived. free5GC answered
with ERROR INDICATION cause protocol 0 (transfer-syntax-error) and Open5GS with
cause protocol 5 (abstract-syntax-error-falsely-constructed-message).

## SKIP and characterisation results

These record behaviour; none is a finding.

- **NGAP-RAN-CONFIG-UPDATE-KEEPS-TA, SD-Core SKIP.** SD-Core answered a RAN
  CONFIGURATION UPDATE carrying only a RAN Node Name with RAN CONFIGURATION
  UPDATE FAILURE, cause misc 5 (unspecified), which TS 38.413 8.7.2.3 permits; the check's
  requirement applies only to an acknowledged update. A registration in the
  tracking area from the NG Setup still succeeded.
- **NAS-BADMAC-REGISTRATION-AFTER-SMC, SD-Core and Open5GS SKIP.** Both
  answered a mobility REGISTRATION REQUEST with a corrupted MAC, sent after
  the security mode control procedure, with an AUTHENTICATION REQUEST.
  TS 24.501 4.4.4.3 can be read to require that, so the check does not grade
  it. free5GC discarded the message (PASS).
- **NGAP-HANDOVER-CANCEL-ACK, SD-Core and Open5GS INFO.** Both acknowledged
  the HANDOVER CANCEL within 5 ms and released the UE context prepared at the
  target gNB.
- **NGAP-NG-SETUP.** All three accepted a valid NG SETUP REQUEST, within 1 ms
  to 9 ms.
- **NGAP-DUPLICATE-RAN-NODE-ID.** All three accepted a second NG SETUP REQUEST,
  from a second source address, presenting the Global RAN Node ID of a live
  association, and kept the first association.
